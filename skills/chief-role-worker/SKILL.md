# Chief-managed worker

Read with the shared `chief-worker` skill; rules that bind two roles (the report contract, verification, deviations) live there.

- Committing and pushing, a blocked split into smaller waves, and lint/build evidence are in your brief's working contract. Do not send extra `chief_report` calls for commit/push checkpoints.
- When your brief has review findings to fix, first verify each finding against the code and the brief, and fix every blocking finding that holds. Do not apply a finding that is wrong or contradicts the brief or plan; list it in your ready result under `## Disputed findings` with evidence (file:line, command output, or the brief or plan text it contradicts).
- When your brief has a `## Verify command`, run it and reach exit 0 before reporting ready; nobody reruns it: reviewers read code only, so report it with its exit status, together with the project's lint/analyze and build after your last commit. Unless you are a tester or Spec Writer (see your role skill), if it runs tests, do not run it: list it as not run (a tester's).
- Never change docs/, on every chain and on unplanned work, with or without a `## Spec` block: list a needed docs change under `## Docs needed` in your ready result. On a spec-bearing chain (your brief has a `## Spec` block), record `Base commit: <sha>` when you start and `Head commit: <sha>` when you report. On a spec wave the plan file is your source of truth: pre-plan specs may be stale, so where they conflict with the plan, follow the plan and name the conflict in your report. A Spec Writer records the change in docs/ in parallel: do not wait for it or implement against its docs. When the Spec delta cannot be built, report blocked and recommend a fresh `chief_plan`. On a legacy chain whose brief says to implement to match the Spec Writer's docs, and the spec is wrong, report blocked and recommend `kind: spec-writer`.
- When your brief names a branch, before you read any file sync the checkout: require a clean tree, run `git fetch origin <branch>` then `git merge --ff-only origin/<branch>`, and record `Local sync: <sha>`. When the fast-forward fails, report blocked. If a push is rejected, run `git fetch origin <branch>` then `git rebase --no-autostash origin/<branch>` on a clean tree and push again. Never use autostash, never force-push, never touch another worktree.
- Unless you are a tester or Spec Writer (see your role skill), never write, edit or run tests of any kind (unit, integration, end-to-end, screenshot or golden): a tester does, after you.
- Before reporting ready, read `git status` and `git diff` in full: no debug prints, stray mock data, secrets, or files the task never needed.
- A worker on a plan run has `chief_log`, a shared log with its peer waves. Call it with no entries before each new sub-problem and before reporting ready: it shows unread peer entries and every wave's current worker and state. Append a `FACT` or `FAIL` (`{kind, text, scope, basis}`) as soon as a finding could change a peer wave's next step: an interface detail, a shared file's real behaviour, a dead end. Your reported `fails` reach it automatically. Never claim, reassign or start another wave's work; if a peer's state blocks you, tell Chief through `chief_report`.
