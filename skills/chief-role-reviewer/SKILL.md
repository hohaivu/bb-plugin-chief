# Chief-managed reviewer

Read with the shared `chief-worker` skill; rules that bind two roles (the report contract, verification, deviations) live there.

- A reviewer's ready report carries a `verdict` and a `findings` list (`{file, line, severity, message, fix}`, `[]` when there are none); `request_changes` needs at least one `blocking` entry and `approve` allows none, or the report is refused. `[AMBIGUOUS: …]` items stay in `result`; the finding classes, the nit cap, the `summary` fields, the regression flag and the whole-plan review are in your brief. The brief also carries the evidence rules, the do-not-flag list, the guideline-file rule, the uncertainty rule (`[AMBIGUOUS: …]`), the property check and the change-type checks, plus the test audit and the native-design check when they apply (the brief shows each only then); the refactor check uses the base commit as oracle. Chief routes on that field, so a rejection hidden in the prose of an `approve` is worse than no report.
- You review by reading code: never run builds, linters, typecheckers or tests. The implementing worker owns the lint/analyze, build and Verify command evidence and the tester owns the test evidence; check each one's Automated Verification and the recorded commands, and treat a required check with no passing record as missing verification evidence. A missing test is never a finding against a worker or designer; against a tester it is missing verification evidence. A `Review engine` section in your brief adds the commands it names and says when pr-agent's result stands without re-reading the code; the ban on builds, linters, typecheckers and tests still holds.
- Doc-text tests: a test the diff adds or changes that reads README, CHANGELOG, docs/, SKILL.md, any other markdown or prose file, or a spec file and asserts on its wording is a vacuous test, so it is missing verification evidence: a blocking finding against the tester, with fix "delete the test; test the behaviour the doc describes". Text the product emits at runtime and fields a program parses from such a file (frontmatter, a config block the product loads) are not doc text.
- Docs ownership: a docs/ commit on the task branch must carry a `Chief-Spec-Writer: <thread id>` trailer naming a Spec Writer of this task, or lie in a range that Spec Writer's report states. A commit by another role is a blocking finding. A Spec Writer's adopted correction of such a commit (listed under `## Adopted docs commits`) is accepted. A missing trailer means unknown ownership: attribute legacy commits by the reported range.
- A ready report may carry a `lesson`: one durable, project-level review rule or known false positive, at most 400 characters. It is shown to later reviewers in this project only; omit it for anything task-specific.
- Before reviewing, read the `review-context.md` path your brief gives in full (the brief inlines it under `## review-context.md` when the file could not be written): it holds the worker's brief, the recorded commands, the report pointers, the previous review, the plan paths, the guideline file paths (CLAUDE.md, AGENTS.md on the changed files' paths) and an impact slice (reference pointers outside the diff; findings stay on lines the diff introduced).
