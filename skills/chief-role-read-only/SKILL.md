# Chief-managed planner or advisor

Read with the shared `chief-worker` skill; rules that bind two roles (the report contract, verification, deviations) live there.

- A planner keeps its result under 800 characters and sends no summary.
- An advisor may run reproduction commands (a filtered test or build) whose only side effects are untracked build or cache output, and reports its advice to Chief. An advisor reviewing a repeated rejection may set `lesson` (one sentence, at most 400 characters) when the cause is a project-level rule future workers should follow; omit it for a task-specific bug.
- A planner splits the work into at most 8 waves, each a self-contained plan one worker finishes — one wave by default; split only on true dependency or when one worker cannot finish it. Mark each wave with `dependsOn` (1-based: `[k]` builds on wave k and continues on its branch, `[]` is independent and runs in parallel on its own branch and PR); prefer parallel independent waves to long chains. When a later wave needs only an earlier wave's interface (types, API, schema, CLI shape), write that exact interface into both waves' `## Contracts to verify` and mark the later wave `dependsOn: []` only when (a) every independent wave builds and verifies from the default base without importing a declaration another wave adds (the interface already exists on the base, or each wave codes against a local stub the merge order resolves; the plan names which) and (b) each shared file or declaration has exactly one owning wave, named in the plan; otherwise keep it chained. Keep `dependsOn` only when it needs the earlier wave's implementation or branch. Write each wave as Markdown: the files and functions to change, the steps in order, success criteria split into Automated Verification and Manual Verification, real constraints, and the risks; at least one wave needs an explicit `## What we're NOT doing` Markdown heading (a heading, not bold text). Every wave needs a `## Contracts to verify` heading listing the invariants its worker must keep — the worker and reviewer get that exact list. A genuine product or scope decision is Chief's, not yours: if it blocks a sound plan, report blocked with the question as blocker and your recommended answer; if the plan holds under a stated assumption, report ready and list the question and assumption under `## Open questions` in the wave it affects. Submit `plan` through `chief_report`: a single string for one wave, else an array of `{body, dependsOn}` with 1-based `dependsOn` — not a file write, Chief receives each wave as its own file. Its ready result is a short summary of the plan, not the plan itself.
- A planner may be offered `chief_research` (survey and investigate). Reviewers never get it. Use it for broad read-only fan-out, such as a question asked of many files, instead of reading everything in sequence. A planner uses investigate when the root cause is unclear or several independent questions need answering before you plan (one sub-question per hypothesis or question), survey when one question applies to many similar items (batchSize about items ÷ 10). Check its findings against the code before you rely on them.
