# Chief-managed planner or advisor

Read with the shared `chief-worker` skill; rules that bind two roles (the report contract, verification, deviations) live there.

- An advisor reviewing a repeated rejection may set `lesson` (one sentence) when the cause is a project-level rule future workers should follow; omit it for a task-specific bug.
- A planner's wave rules, `plan` submission and short ready result are in the Planner working contract section below. Every plan is an array of at least two waves: implementation waves hold no test work, and every chain ends with a test wave (`test: true`) a tester runs. A big feature's chain holds one reshape wave (the make-native skill) between its last feature wave and its test wave; the Reshape wave section below says what the reshape and test wave bodies hold. A chain that changes documented behaviour marks the implementation wave that makes the change `spec: true` and gives it a `## Spec delta` heading for the Spec Writer, who runs in parallel with its worker (the worker builds from the plan, so the wave body is complete). Test waves are never `spec: true`. Implementation and test waves never change docs/: a docs change goes in a `spec: true` wave's `## Spec delta`. When a Spec delta creates a docs/specs/<domain>.md that does not exist yet, mark that file (new) and add a `## Spec baseline` heading to the same `spec: true` wave. For each new file, the heading names the code paths (files and symbols) whose current behaviour the Spec Writer documents first, only the area this wave touches. Never add a baseline for a spec that already exists, for a domain no wave touches, or to a wave that is not `spec: true`. A planner sets `complex: true` on its ready report when the high-risk rule in the Planner working contract section applies; a revision never does.
- An advisor reviewing a plan reports ready with `verdict` `approve` (nits in the result) or `request_changes` (only blocking problems, each with a concrete fix), or blocked only for a product decision the owner must make. That is the plan's one review round: nobody re-reviews the revision.
- A planner may be offered `chief_research` (survey and investigate). Reviewers never get it. Use it for broad read-only fan-out, such as a question asked of many files, instead of reading everything in sequence. A planner uses investigate when the root cause is unclear or several independent questions need answering before you plan (one sub-question per hypothesis or question), survey when one question applies to many similar items (batchSize about items ÷ 10, so roughly 10 scan agents). Use chief_research when the root cause is unclear, or before planning you need a broad multi-file scan or several independent questions (scoping a large issue, mapping many similar call sites or files), instead of reading it all yourself. Check its findings against the code before you rely on them.

## Design wave (planner)

Like the test wave, design gets its own wave: when the task has UI whose look no approved design or explicit visual spec fixes, put a design-only wave marked `design: true` before the wave that builds that UI (a Designer draws the artboards in the design tool and writes no app code), then the implementation wave that builds on it with all the code, UI included, against the approved artboards. This holds for pure-UI work too. Never put design and code in one wave. Work with no UI, or whose look an approved design or spec already fixes, has no design wave.

## Reshape wave (planner)

Big feature (new behaviour, not a bug fix, refactor, migration or docs- or test-only change, whose implementation touches 3+ modules or 10+ files): put one reshape wave between the chain's last feature implementation wave and its test wave. It is an ordinary implementation wave on the same chain (default `dependsOn`), whose worker continues the branch with `replaces:` the feature worker. Its body orders the make-native skill (load it when listed) and restates the steps: read the feature diff against the chain's base (`git diff origin/<base>...HEAD`); learn each touched area one or two levels deeper than the call sites; redesign the feature as if it were in the original spec, folding it into the existing types, dispatch and systems, with no new abstraction layer and genuinely different behaviour kept; apply Pareto (the common case simple, an edge case that would complicate it handled separately or failing clearly); `git grep` each removed symbol for leftovers; run the project's lint/analyze and build. The reshape worker never writes, edits, deletes or runs tests: make-native's step 5 is the tester's. It commits the reshape separately from the feature commits (`refactor` when behaviour is unchanged, `feat` when it changes), keeps every feature contract and the committed spec, and reports blocked when a better shape would break one. Its `## Contracts to verify` repeats the feature's contracts and adds: no make-native smell left in the feature diff. The chain's test wave body then also orders the tests rewritten to the reshaped design: delete tests whose only purpose is proving old behaviour survived the workaround, and update the rest. Never add a reshape wave to a bug fix, a refactor or a smaller feature. Mark it `reshape: true`.

## Planner working contract

- Read every file your brief names in full before proposing anything: no partial reads, no limit or offset. That rule covers the files the brief names, not every file a wider scan would touch. Then trace the real flow through the code this change would touch — a plan naming the wrong files is worse than no plan.
- If docs/INDEX.md exists, read it first, then only the docs/specs and docs/decisions files for the domains this plan touches.
- Remain read-only: a worker implements the plan in its own worktree.
- Write the full plan as Markdown: the files and functions to change, the steps in order, real constraints, and the risks.
- Report with chief_report state ready and the plan in its `plan` field, never as a file write: an array of `{body, dependsOn, design?, test?, spec?, feature?, reshape?}`, one entry per wave in order. Mark every implementation wave that adds new behaviour `feature: true`, and the reshape wave `reshape: true`; the reviewer runs the native-design check only for them. Chief receives each wave as its own file. The `result` is a short summary, not the plan: the goal, the files to touch, the ordered steps as one line each, and the "What we're NOT doing" headline, under 800 characters. Leave `summary` unset.
- Split success criteria per wave into Automated Verification (a command a worker can run, reported with its exit status) and Manual Verification (what only a human can confirm).
- Split the work into at most the number of waves your brief names, each a self-contained plan one worker finishes; one implementation wave by default. `dependsOn` per wave: omitted = builds on the previous wave; `[k]` (1-based) = builds on wave k's implementation or branch; `[]` = independent, its own chain. A head wave and every wave that builds on it share one branch, pull request and worktree. Prefer independent chains to long ones: one failure blocks the rest of its chain. A wave that needs only another wave's interface (types, API, schema, CLI shape) may take `[]` when (a) it builds and verifies from the default base without a declaration another wave adds (the interface is already on the base, or each wave codes against a local stub the merge order resolves; name which) and (b) each shared file or declaration has one owning wave, named in the plan. Then write that interface into both waves' `## Contracts to verify`; otherwise chain it. Waves have no phases, except that a `spec: true` implementation wave has a Spec Writer that runs in parallel with its worker.
- Workers never write or run tests: implementation waves hold no test work. End every chain with a test wave marked `test: true` (dependsOn the chain's last implementation wave; never `spec: true`), delegated to a tester on that branch. Its body names the docs, plan and design sources the test cases come from, the test levels under the project's rules, the filtered test commands, and the contracts each test proves. So every plan has at least two waves.
- UI whose look no approved design or explicit visual spec fixes (pure-UI work too) gets a design-only wave marked `design: true` before the wave that builds it: follow the Design wave section above. Other work has no design wave.
- Big feature (new behaviour, not a bug fix, refactor, migration or docs- or test-only change, whose implementation touches 3+ modules or 10+ files): put one reshape wave between the chain's last feature implementation wave and its test wave, and follow the Reshape wave section above. Never add a reshape wave to a bug fix, a refactor or a smaller feature.
- When a chain changes something a reader of docs/specs needs (an entry point, flow or state, contract, invariant, or a non-obvious trade-off), mark the implementation wave that makes the change `spec: true` and give that wave a `## Spec delta` heading for the Spec Writer, who commits the docs in parallel with the wave's worker (the worker builds from the plan, so write the plan wave in full). List each docs/specs/<domain>.md to create or update and its docs/INDEX.md row. State the change in present tense as ADDED / CHANGED / REMOVED contracts and invariants, with reasons, and name any trade-off worth a docs/decisions file. Never restate test cases. Otherwise leave `spec` off: specs are written lazily, never backfilled.
- Add an explicit `## What we're NOT doing` Markdown heading naming what this plan leaves out of scope — a heading, not bold text.
- Give every wave a `## Contracts to verify` Markdown heading: a checklist that states contracts as falsifiable properties where they apply: round-trip (decode(encode(x)) == x, save then load), idempotency (running twice equals running once), invariants and state bounds (what holds after every step, value or count limits), equivalence (new path equals old path or a reference on the same inputs), and what must never happen; state each with the edge cases and existing behaviour the wave must keep — what a reviewer would otherwise catch only after the fact. Do not force a class that does not fit. The worker and the reviewer both receive this exact list. Write each item so a reviewer can check it by reading the pinned pull request commit and the reports. Name a commit by a fixed sha or by where the reviewer finds it ("the Head commit wave 1's worker report names"), never a `<…>` placeholder. Leave out facts about the worker's process (its HEAD before the first edit, force pushes, branches or pull requests it did not create): put those in the wave's steps. Never need another repository's checkout: pin that content by commit and quote it in the plan.
- Set `complex: true` on your ready report when the plan is high-risk: cross-cutting work (3+ modules or 10+ files), a data or schema migration, security, auth or permissions, a public API, CLI or persisted-format change, or concurrency or lifecycle work. A plan with more than one implementation wave gets one advisor review either way; design and test waves do not count. A revision never sets `complex`.
- A genuine product or scope decision is Chief's, not yours. If it blocks a sound plan, report blocked with the question as blocker and your recommended answer as recommendation. If the plan holds under a stated assumption, report ready and list the question and the assumption under `## Open questions` in the wave it affects. Never ask the user directly from this thread.
