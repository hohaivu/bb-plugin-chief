# arXiv 2609.20804: harness design for coding agents, and what it means for Chief

Research note, 2026-10-13. Written so that future PRs and Chief briefs can cite one finding at a time: link `docs/research/2609.20804-harness-design-for-coding-agents.md#f1` (F1 to F10).

Conventions in this doc:

- **Paper** = stated in the paper (v1). Numbers are copied from the paper's tables and text, checked against the file. "pp" = percentage points. The paper sometimes writes "%" where it means pp; this doc reads those as pp and says so.
- **Our inference** = not stated in the paper. Never treat it as the paper's claim.
- Quotes are short and come from v1 with the PDF-extraction formatting removed (stray underscores, curly quotes).

## Paper

| | |
|---|---|
| Title | An Empirical Study of Harness Design for Coding Agents |
| Authors | Run-Ze Fan, Zihao Zhang, Simin Ma, Yebowen Hu, Shouju Wang, Kaiqiang Song, Fei Liu, Hamed Zamani, Xiaoyang Wang |
| Affiliations | UMass Amherst, Emory University, UNC Charlotte (the paper also notes internships at Zoom Video Communications) |
| arXiv | 2609.20804 (v1). Link: <https://arxiv.org/abs/2609.20804>. The id comes from the attachment file name and the arXiv abs page title; the paper text does not print it. |

**Summary.** The authors build a small coding harness with a fixed ReAct loop and vary three components one at a time: planning, the action space (predefined tools vs bash only), and context management (five strategies, T0 to T4, under 32k to 128k context windows). They test four open-weight models (Nemotron-3 30B, 120B, 550B and Mistral-Medium-3.5-128B) on SWE-Bench Verified and Terminal-Bench 2.1, 176 matched settings in total (Sec 1, Sec 3.1). Every effect depends on model capability, task type or budget. Context management matters most when the window is tight. Planning raises success for the weakest model and mostly saves cost for stronger ones. Predefined tools help bash-weak models, while bash-capable models do as well or better with bash only and cost less. An appendix also checks an LLM judge (GPT-5.5, high effort) against human labels on trajectory annotations (App C.2). The paper never tests a separate planner writing a plan for another model, never compares judges of different strength, and never varies reasoning effort.

## Key findings

Each finding has a stable anchor. "Number" is what the paper reports; "Not claimed" is what a reader might wrongly infer.

<a id="f1"></a>
### F1

**Planning raises success for the weakest model.**

- Number: Nemotron-3 30B, planning on vs off at T4/128k: SWE-Bench 25.2 vs 13.6 (+11.6 pp), Terminal-Bench 13.48 vs 8.99 (+4.5 pp). Mean cost per task: SWE $0.09 vs $0.02, Terminal-Bench $0.14 vs $0.08 (+75%, Sec 4).
- Source: Sec 3.2 ("Planning improves success rate..."), Tables 3 and 4 (T4 and T4 w/o plan rows), Fig 6.
- Quote: "planning increases success rate by 11.6 percentage points on SWE-Bench and 4.5 points on Terminal-Bench"
- Caveat: only the SWE-Bench 30B cell carries the significance star (McNemar, q < 0.05); the Terminal-Bench gain is not significant.
- Not claimed: that planning helps a Claude- or GPT-class worker, or that a plan written by another model does the same.

<a id="f2"></a>
### F2

**For stronger models, planning mainly cuts cost, with small changes in success.**

- Number (T4/128k, planning on vs off): Nemotron-3 550B SWE-Bench 65.8 vs 67.8 (-2.0 pp), cost $2.33 vs $3.31 (about -30%); Mistral SWE-Bench 68.6 vs 69.0 (-0.4 pp), $3.14 vs $4.65 (about -32%). Terminal-Bench cost: 120B about -26%, 550B -3.6%, Mistral about -40%. Nemotron-3 120B shows no consistent success gain, and its SWE-Bench cost goes up ($0.34 vs $0.25).
- Source: Sec 3.2, Sec 4 (Terminal-Bench cost paragraph), Tables 3, 4, 5, Fig 6.
- Quote: "planning reduces cost on both benchmarks, accompanied by small decreases in success rate"
- Caveat: none of the stronger-model cells is significant for success rate. Significance is not tested for cost. Each setting ran once per task (Limitations).
- Not claimed: that planning is free for strong models; the success changes are small, but they are all negative or zero in the strong-model cells.

<a id="f3"></a>
### F3

**Mechanism for the weak model: planning keeps the run alive long enough to attempt an edit.**

- Number: Nemotron-3 30B on SWE-Bench, median trajectory 40 turns with planning vs 5 without. Runs ending with no edit: 27.8% with planning vs 68.6% without. Runs that never got past localization: 10.4% vs 58.4%.
- Source: Sec 4 ("Planning sustains the weakest model's trajectory..."), Table 6, Table 12, Fig 8.
- Quote: "Planning sustains the weakest model's trajectory long enough to attempt an edit."
- Not claimed: that the plan's content improves the edit; the paper attributes the gain to the trajectory not stopping early.

<a id="f4"></a>
### F4

**Mechanism for stronger models: planning trims redundant post-edit verification.**

- Number: SWE-Bench median trajectory with vs without planning: Nemotron-3 550B 74 vs 108 turns, Mistral 53 vs 68. Change from planning off to on (Table 5, SWE-Bench): 550B turns -24.3%, tool calls -24.5%; Mistral turns -23.2%, tool calls -23.3%. Runs ending with no edit stay at or below 2.4% (Table 12).
- Source: Sec 4 ("Planning shortens SWE-Bench trajectories..."), Table 5, Table 11, Table 12, Fig 8.
- Quote: "planning primarily improves stopping behavior by reducing redundant post-edit verification, rather than accelerating localization or repair"
- Not claimed: that the removed verification was useless. The paper calls it redundant for these models on these benchmarks.

<a id="f5"></a>
### F5

**A weak model fails early (file localization); stronger models fail late (patch quality).**

- Number: earliest failed stage of unresolved SWE-Bench runs at T4/128k (Table 10), file localization / patch implementation: Nemotron-3 30B 56.3% / 32.4%; 120B 44.3% / 44.6%; 550B 16.4% / 64.9%; Mistral 16.0% / 60.3%. For 30B, file localization rises to 73.8% without planning and 76.6% with bash only.
- Source: App C.3.1 (failure-stage results), Table 10. The stage labels are assigned by an LLM judge (Fig 41), validated in F6.
- Quote: "for Nemotron-3 30B, more than half of unresolved runs fail at file localization"
- Not claimed: anything about narrowing the question. The paper does not test it.

<a id="f6"></a>
### F6

**One strong LLM judge agreed closely with human annotators on trajectory labelling.**

- Number: 200 trajectories, 15,610 labelled units, three annotators, each labelling a separate split. Overall raw agreement about 94.2%, weighted mean Cohen's kappa 0.929. Per split: agreement 88.7% to 98.4%, kappa 0.858 to 0.980. By unit type, kappa: SWE-Bench action labels 0.881 to 0.984, Terminal-Bench action labels 0.758 to 0.965, failure-stage diagnosis 0.813 to 1.000 (50 diagnoses). Judge setup: GPT-5.5, high reasoning effort, temperature 0.6.
- Source: App C.2.
- Quote: "Aggregating across the three splits gives approximately 94.2% raw agreement and a weighted mean Cohen's κ of 0.929."
- Not claimed: that a strong judge is required. No weaker judge is compared. The task is labelling the purpose of turns and the stage of failure, not judging code correctness or PR quality. The kappa of about 0.93 shows one strong judge works for this labelling; it says nothing about whether a cheap judge would fail.

<a id="f7"></a>
### F7

**Predefined tools help weak models; bash-capable models can do as well or better with bash only, at lower cost.**

- Number: bash only vs full tools at T4/128k. Nemotron-3 30B SWE-Bench 10.2 vs 25.2 (paper: "15.0%", read as pp). Nemotron-3 550B SWE-Bench 69.4 vs 65.8 with cost $1.11 vs $2.33 (-53%); Terminal-Bench 50.56 vs 44.94 with cost -30%. Mistral: SWE-Bench 45.4 vs 68.6 (-23.2 pp) but Terminal-Bench 43.82 vs 37.08 (+6.7 pp).
- Source: Sec 3.2 (last paragraph and Takeaway), Tables 3 and 4, Fig 7.
- Quote: "The predefined tool set scaffolds weaker models that cannot reliably express intent through bash alone"
- Caveat: the intervention bundles tool availability, prompts, file-state tracking and post-edit diagnostics (Sec 2.2, Limitations).

<a id="f8"></a>
### F8

**Context management matters most when the window is tight; the staged T4 policy is the cheapest.**

- Number: average gap between managed tiers (T1 to T4) and no management (T0), 32k to 128k windows: SWE-Bench 35.7, 15.9, 5.5, 2.7 pp; Terminal-Bench 9.5, 7.5, 4.8, 2.8 pp. T0 window-overflow failures fall from 78.7% to 8.7% (SWE-Bench) and 61.0% to 12.1% (Terminal-Bench); managed tiers have zero overflow. T4 has the lowest cost in seven of eight model/benchmark panels.
- Source: Sec 3.2 (first two paragraphs), Tables 3 and 4, Figs 3 to 5.
- Quote: "Context management reduces the sensitivity of task success to context-window capacity, enabling effective execution under tighter context budgets."

<a id="f9"></a>
### F9

**Making elided context recoverable adds machinery that models rarely use.**

- Number: T2 (recall) vs T1 (elision only): better in 15 of 32 comparisons, worse in 14, tied in 3; mean difference -0.36 pp. 36 of 64 recall-enabled settings never call `recall_event`. Mean calls per task fall from 0.540 at 32k to 0.069, 0.011, 0.007 at 64k, 96k, 128k.
- Source: Sec 3.2 ("Recall (M2) is rarely used..."), Table 13.
- Quote: "lossless storage adds machinery most models seldom use"

<a id="f10"></a>
### F10

**The paper's conclusion: harness components are conditional, and crossover points need re-validation.**

- Number: none; it is the paper's framing of the 176-setting study.
- Source: Sec 6 (Conclusion), Limitations.
- Quote: "each component should be selected for the target model, task type, and resource budget rather than adopted as a default"
- Caveat (Limitations): planning and the action space are ablated only at T4/128k; one run per task; Terminal-Bench has only 89 tasks, so many contrasts are not significant; model size is "an imperfect proxy for capability".

## Open questions / experiments to run

Each is a hypothesis to measure in Chief's own data, not something the paper settles.

1. **Does a planner-written plan help a weaker worker?** (F1, F3, F4.) Compare planned vs unplanned worker runs on matched tasks. Metrics: reviewer request-changes share, review rounds per task, and the share of runs that stop with no edit. This is D5's one-week check; keep it separate from the effort change if possible.
2. **Is a strong judge needed?** (F6.) Run a cheap and a strong reviewer on the same recent PRs. Score both against the eventual human or merge outcome with Cohen's kappa, as the paper did for its judge, on a sample of about 50 to 200 cases.
3. **Does narrowing the question help cheap researchers localize?** (F5.) Give `investigate` and `survey` an open question and a narrowed version of the same task. Measure whether the right file or log is found.
4. **Does a plan cut worker verification, and is that wanted?** (F4.) Count verification steps per worker run with and without a plan, and whether the reviewer later finds problems that verification would have caught.
5. **Does effort matter separately from plan quality?** (all.) The paper has no effort data. Test planner and worker effort one at a time, not as a package, if the package result is ambiguous.
6. **Label Chief runs with the paper's phase scheme** (App C.1.2: localize, reproduce, fix, verify, other) to see where weak or cheap runs stop. A cheap way to check D6 before any Haiku trial.
7. **Does the weaker-model regime apply to any Chief role at all?** No Chief model has been placed on the paper's weak-to-strong scale. Treat the 30B results as a description of a failure mode (stopping early, failing to localize), not as a capability line.

## Limits

Where the paper's setup differs from Chief's:

- **Planning is self-authored.** The paper's plan is a todo list the executing model keeps with `update_plan`, injected each turn (Sec 2.1). The authors say their results estimate this scaffold, not planning as a general reasoning strategy. Chief's planner is a separate, stronger model writing a plan that another model executes. That handoff is untested.
- **No judge strength comparison.** The one judge tested (GPT-5.5, high effort, temperature 0.6) labels trajectory turns and failure stages. Chief's reviewers judge diffs for merge. Different task, no weak-judge baseline.
- **No reasoning-effort axis.** Temperature is 0; effort levels are not varied for the agents.
- **Different models.** Nemotron-3 (30B, 120B, 550B) and Mistral-Medium-3.5-128B, served locally in BF16. No Claude, GPT or Haiku models. "Weaker" means a 30B open model with 9.40 to 26.40% success across its SWE-Bench settings (Table 3); a Claude or GPT model's position on that scale is not known, and the paper warns that size is only an imperfect proxy for capability.
- **Different tasks.** SWE-Bench Verified (500 Python issues) and Terminal-Bench 2.1 (89 tasks), each solved in a single agent run with up to 300 steps. Chief tasks are plugin and PR work with a worker, a reviewer and review rounds. The paper has no review loop.
- **Thin statistics.** One run per task. Planning and action-space ablations only at T4/128k. Of the planning contrasts, only the 30B SWE-Bench success change is significant (Tables 3 and 4); cost differences are not tested. Terminal-Bench is small.
- **Bundled interventions.** The action-space change also alters prompts, file-state tracking and diagnostics (Sec 2.2).
- **Cost.** Dollar costs use OpenRouter prices for these models (Sec 3.1), not Chief's providers.
- **Context management** (F8, F9) is studied under hard windows of 32k to 128k tokens. Whether Chief threads hit such limits is not established here.
